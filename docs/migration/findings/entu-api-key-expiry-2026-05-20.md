## 0. Authoritative mechanism (Argo, definitive)

API keys are NOT standalone resources. They are a special property type `entu_api_key` on an entity (typically a person entity).

### Generation & storage

When a property of type `entu_api_key` is POSTed to an entity (`POST /[db]/entity/[_id]`), `setEntity()` (entu-api `utils/entity.js:469-472`):

1. Generates `randomBytes(32)`, each byte mapped via modulo 65 onto an alphanumeric+symbol charset → ~43-char raw key
2. Hashes the raw key with `createHash('sha256').update(apiKey).digest('hex')`
3. Stores ONLY the SHA-256 hash, at `entity.private.entu_api_key.string`
4. Returns the raw key to the client exactly once — never persisted

A unique index on `private.entu_api_key.string` (`utils/setupDatabase.js:225`) makes auth lookups fast.

### Authentication flow

`GET /auth/` (entu-api `routes/auth/index.get.js`):

1. Extract Bearer token from `Authorization: Bearer <key>` (line 95)
2. SHA-256 hash the extracted key (line 119)
3. Look up the hash in `entity.private.entu_api_key.string` across accessible account DBs (lines 148-151)
4. Resolve owning person entity → account + user
5. Issue a 48-hour JWT encoding `accounts: { [db]: user_id }` (line 259)
6. `middleware/auth.js:46-48` later uses this JWT to resolve the user on `/[db]/` routes

**Fallback:** If API-key auth fails (hash not found), the endpoint falls back to JWT session validation. If THAT also fails, the response is effectively anonymous — JWT issued without `accounts` mapping.

## 1. Does the API key expire?

**Short answer: The API key itself does NOT auto-expire. It is permanent.**

Per the mechanism above: the key is just a hash stored as an entity property. There is no TTL, no rotation timer, no expiry timestamp. The key remains valid until the property is updated/overwritten OR the owning entity is deleted.

The 48-hour expiry applies to the **JWT** minted from the key — not the key itself.

### Terminology clarification

The credentials file (now corrected) previously called `ENTU_API_KEY` the "temporary API key." This was misleading. Entu's auth surface has these distinct token types:

| Token type | Generated by | Storage | Lifetime |
|---|---|---|---|
| **Session token** | OAuth callback `{"key": ...}` | Short-lived (probably similar entity-property pattern with TTL) | Single-use / session |
| **API key** (what we have) | `POST` of `entu_api_key` property type on a person entity | SHA-256 hash in `entity.private.entu_api_key.string`, unique-indexed | **Permanent** (no auto-expiry) |
| **JWT** | `GET /auth?db=<db>` exchange | Client-held; encoded with `accounts: {[db]: user_id}`, `iat`, `exp`, `aud` | **48 hours**, IP-bound via `aud` |

## 2. What happened to the 2026-05-18 key (session 7 auth diagnostic)?

**Root cause: PO's manual rotation in the Entu UI overwrote the `entu_api_key` property on the person entity.**

Per Argo's flow:
- Old key's raw value still produces a valid SHA-256 hash
- That hash is no longer present in the index (the property was overwritten with the new key's hash)
- Auth lookup fails at step 3 (hash not found)
- Falls back to JWT validation — old key isn't a JWT either, that fails too
- Endpoint issues an anonymous JWT (no `accounts` mapping) and returns it

That's exactly what was observed: `accounts: []` from the old key after rotation. The old key is "alive" only in the sense that the Bearer token format is still valid; semantically it's dead.

### Implications for client code

- Clients can't tell from the Bearer key value alone whether it's "live" or "dead-after-rotation"
- The signal is in the JWT response: `accounts: []` means the key didn't resolve to any db
- Robust clients should check `accounts.length > 0` after `GET /auth?db=...` before proceeding

## 3. JWT IP-binding note (operational gotcha)

The JWT `aud` claim encodes the client IP at mint time. Entu verifies `aud` on each API call. **If the calling IP changes between JWT mint and API use, the JWT will silently fail.**

Implications:
- Not a concern for local dev (stable IP)
- Could cause silent failures in dynamic-IP environments: CI runners, NAT rotations, dev container rebinds
- For long-running migration runs (Phase B with snapshot + N+1 fetches): all calls happen within seconds of JWT mint, so IP stability is preserved
